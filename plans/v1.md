# Studybuddy v1 — Design

## Overview

A single-user flashcard study app for an 8th grader preparing for finals. Delivered as a Progressive Web App installed via "Add to Home Screen" on iPhone. Decks are authored by the developer (parent) using a Claude Code skill in the repo that converts teacher-supplied study guides (PDFs, images) into flashcard JSON files. The PWA is a pure static site with no backend, no authentication, and no AI calls at runtime.

## Goals

- Help one specific user drill flashcards for finals.
- Maximize memory retention through a clean, low-distraction UI grounded in cognitive-load research.
- Zero operational cost and zero ongoing maintenance.
- Fast dev iteration — "push to main, she has the new deck."

## Non-goals (v1)

- Multi-user support, auth, or cloud sync.
- Homework/to-do tracking (original v1.md scope, deferred).
- Study-guide rendering as in-app content (study guides are dev-side input only).
- AI features inside the app (LLM work lives in a repo-local Claude skill, not at runtime).
- Cross-session card state, spaced repetition, or streaks.
- App Store distribution.

## Users & Usage Context

- **Primary user:** one 8th grader (13+), iPhone, installs via Safari "Add to Home Screen."
- **Developer:** parent builds and maintains; daughter provides feedback.
- **Session shape:** cramming-for-a-test — opens the app, picks a recent deck, drills until she's gotten every card right once, closes. No daily-habit expectation.

## Architecture

### Runtime

- Pure static PWA. No backend, no serverless functions, no database.
- All flashcard content bundled into the JS bundle at build time.
- Session state (which cards are missed within a session) lives in React state only; nothing persists across sessions.

### Build & Deploy

- **Stack:** Vite + React + TypeScript + Tailwind CSS.
- **Hosting:** GitHub Pages, deployed from `main` via GitHub Actions on push.
- **Deck discovery:** `import.meta.glob('/src/decks/*.json', { eager: true })` — Vite picks up every JSON file under `src/decks/` at build time. No manifest to maintain.

### Content Authoring Flow

1. Teacher provides a study guide (PDF, images).
2. Developer runs a Claude Code skill in the repo (to be built separately, out of scope for this design) that:
   - Reads the study guide.
   - Produces a flashcard JSON file at `src/decks/<slug>.json`.
3. Developer reviews, commits, pushes to `main`.
4. GitHub Actions builds and deploys.
5. On next launch, the PWA shows the new deck.

## Data Model

One JSON file per deck in `src/decks/`. File name is unconstrained; the app reads metadata from inside the file.

```json
{
  "id": "algebra-finals-2026-05",
  "name": "Algebra Finals Review",
  "createdAt": "2026-05-02",
  "cards": [
    { "front": "What is the quadratic formula?", "back": "$x = \\frac{-b \\pm \\sqrt{b^2 - 4ac}}{2a}$" },
    { "front": "Define *slope*.", "back": "The ratio $\\frac{\\Delta y}{\\Delta x}$ — how steep a line is." }
  ]
}
```

- `id` — stable string; used as React key and for any future routing.
- `name` — display name shown in the deck list and deck cover.
- `createdAt` — ISO date; used to sort decks most-recent-first.
- `cards[]` — each card has `front` and `back` only. Both are Markdown strings that may contain inline LaTeX (`$...$`) or block LaTeX (`$$...$$`). No other card types, no per-card metadata.

## Screens & Navigation

Single-tab app (no tab bar in v1 since Flashcards is the only feature). Three screens, stack navigation:

### 1. Deck List (home)

- Header: "Studybuddy" (or similar).
- List of decks, sorted by `createdAt` descending (most recent first).
- Each row: deck name + card count (e.g. "24 cards"). Tapping a row pushes to Deck Cover.

### 2. Deck Cover

- Large deck name.
- Card count.
- Single primary button: **Start studying**.
- Back button to Deck List.

### 3. In-Session

Layout top-to-bottom:

- **Top bar:** progress indicator (e.g. "7 / 20") and an exit (✕) button.
- **Card area:** large, centered. Card front shown initially. Tap the card to flip; tap again to flip back.
- **Action row (shown only after flip):** two buttons — **Got it** (green) and **Missed it** (red).

Session mechanics:

- Cards are **shuffled** at the start of each session.
- On **Got it**, the card is removed from the session pool; advance to the next card (unflipped).
- On **Missed it**, the card is pushed to the end of the session pool to appear again later in this session.
- Session ends when the pool is empty (every card has been marked Got it at least once).
- Exit (✕) aborts the session and returns to Deck Cover; no partial-session save.

### 4. Results

Shown when the session ends:

- "Done!" headline.
- Session time (mm:ss).
- "First-try: N" / "Needed retries: M" counts.
- List of card fronts she needed retries on (truncated or scrollable, no scoring).
- Buttons: **Study again** (restarts shuffled session) and **Back to decks**.

## Look & Feel

Design philosophy: optimize for memory retention, not engagement. Research basis — high contrast aids reading, low clutter preserves cognitive resources for encoding, semantic (not decorative) color aids recall, seductive details hurt learning.

- **Base:** light mode only in v1. Near-white background, near-black text. Dark mode deferred.
- **Palette:** neutral base + exactly two semantic accents — green for "Got it," red for "Missed it." No additional decorative colors.
- **Typography:** system sans-serif (San Francisco on iOS). Large, readable card text. No decorative fonts.
- **Layout:** generous whitespace around the card. Card is visually dominant on the In-Session screen. Predictable, static element positions — no motion that moves buttons around.
- **No:** mascots, illustrations, streaks, celebration animations, sound effects, gamified counters.
- **Yes:** subtle card-flip animation (rotateY), subtle press state on buttons. Motion used only to signal state changes, never for delight.

## Rendering

- Markdown rendered with a small library (e.g. `react-markdown`).
- LaTeX rendered with KaTeX (via `rehype-katex` + `remark-math`). Inline `$...$` and block `$$...$$`.
- Card content is dev-authored and committed; HTML sanitization is not a security requirement for v1 (single trusted source), but we'll use the default-safe renderer anyway.

## PWA Configuration

- Web app manifest with name, icon set, `display: standalone`, and theme color matching the app background.
- Service worker for offline: caches the app shell and all bundled deck JSON. Since decks are bundled, offline = fully functional.
- Icon: a single 512×512 PNG for v1, scaled. No adaptive/maskable variants yet.

## Out-of-Scope / Future

Flagged here so they don't get rediscovered later:

- Homework tab (deferred per user decision).
- Study-guide rendering as in-app content.
- Cross-session card state and spaced repetition.
- Dark mode.
- Deck deletion/hiding from the UI.
- Image-containing cards.
- Multiple choice or other card types.
- Backend proxy + AI features at runtime (deferred; may return if study-guide → deck becomes app-driven instead of dev-driven).
- App icons / adaptive icons / splash screens beyond the minimum.

## Open Questions

None blocking. The Claude skill that turns study guides into deck JSON is a separate design.
